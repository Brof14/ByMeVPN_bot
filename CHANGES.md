# Список исправлений (аудит и фикс от 26.06.2026)

Ниже — все найденные баги, в порядке критичности. Каждый пункт указывает
файл, причину и что именно изменено. Комментарии с тегом `FIX:` оставлены
прямо в коде на месте каждого изменения.

## Критичные (объясняют исходные симптомы)

### 1. `sqlite3.OperationalError: unable to open database file`
**Файл:** `database.py`
Папка `data/` для файла БД (`data/vpnbot.db`) не создавалась автоматически —
`aiosqlite`/`sqlite3` никогда создают родительские директории сами.
**Фикс:** добавлен `os.makedirs(os.path.dirname(DB_FILE), exist_ok=True)`
перед первым подключением.

### 2. Два независимых пути к базе данных
**Файлы:** `config.py`, `database.py`
`config.py` определял свой `DB_FILE` (из `.env`, дефолт `vpnbot.db`),
а `database.py` — свой захардкоженный (`data/vpnbot.db`). `handlers/admin.py`
и `notifications.py` импортировали `DB_FILE` именно из `config` — то есть
бэкапы и "размер БД" в админ-панели смотрели в файл, никак не связанный
с реальной рабочей базой.
**Фикс:** `database.py` теперь единственный источник правды (читает тот же
`.env`-параметр), `config.py` ре-экспортирует значение оттуда же.

### 3. Кэш статуса пользователя был общим для разных функций
**Файл:** `cache.py`
Декоратор `@cache_user_info` кэшировал результат под ключом `f"user_{user_id}"`
— одинаковым для `has_trial_used`, `has_active_subscription`, `has_ever_had_key`,
`get_user_active_keys`, `has_paid_subscription`. Эти функции вызывались
параллельно через `asyncio.gather` в `handlers/start.py`, и какая первая
запишет в кэш — её результат (bool или list) подменял результат всех
остальных на 5 секунд. Это причина того, что бот мог показывать неверный
статус подписки/количество ключей.
**Фикс:** ключ кэша теперь включает имя функции (`f"user_{func.__name__}_{user_id}"`).
`invalidate_user_cache` переписана, чтобы чистить все записи пользователя
по всем функциям сразу.

### 4. `NameError` маскировал реальные ошибки выдачи ключа
**Файл:** `subscription.py`
В `deliver_key` стоял `except aiogram.exceptions.TelegramForbiddenError`, но
модуль `aiogram` целиком не был импортирован (только конкретные имена через
`from aiogram import ...`). Любая реальная ошибка при выдаче ключа (например,
сбой 3x-ui) приводила не к понятному сообщению, а к `NameError` внутри
обработчика ошибок.
**Фикс:** `from aiogram.exceptions import TelegramForbiddenError`, обращение
напрямую по имени.

### 5. После оплаты YooKassa бот не выдавал ключ
**Файл:** `webhook.py`
`FSMContext(dispatcher=None, bot=bot, user_id=user_id, chat_id=user_id)` —
неправильная сигнатура конструктора для aiogram 3.x (нужны `storage` и
`StorageKey`). Вызов падал с `TypeError`, который тихо проглатывался
`except Exception`. FSM-состояние "жду имя конфига" никогда не
устанавливалось — пользователь вводил имя конфига, фильтр состояния не
срабатывал, сообщение уходило в fallback, ключ не выдавался.
**Фикс:** `FSMContext(storage=dispatcher.storage, key=StorageKey(bot_id, chat_id, user_id))`.

### 6. Сервер для приёма вебхуков YooKassa никогда не запускался
**Файл:** `main.py`, `webhook.py`
`start_webhook_server` импортировался, но не вызывался — порт никогда не
слушался, `dispatcher`/`bot` в модуле `webhook.py` оставались `None`.
Дополнительно: старая версия функции вызывала `bot.set_webhook(...)` для
Telegram-обновлений, что конфликтует с long polling, который использует
`main.py` (Telegram не разрешает одновременно webhook и polling — 409 Conflict).
**Фикс:** добавлен `asyncio.create_task(start_webhook_server(bot, dp))` в
`main.py`; убран вызов `bot.set_webhook()` — сервер теперь только принимает
`/webhook/yookassa`, Telegram-обновления продолжают идти через polling.

### 7. Кнопка "Забрать 3 дня бесплатно" по реферальной ссылке падала
**Файл:** `handlers/start.py`
`cb_claim_trial` импортировал `from database import create_key` — такой
функции не существует (есть `add_key`). Каждый клик по этой кнопке
приводил к `ImportError`.
**Фикс:** обработчик переписан на использование `subscription.deliver_key`
(тот же проверенный путь выдачи ключа, что и везде), добавлена атомарная
проверка через `try_claim_trial`.

### 8. Кнопка активации реферального бонуса (+15 дней) падала
**Файл:** `handlers/keys.py`, `database.py`
Импортировалась `from database import try_claim_ref_bonus` — такой функции
не было (существовали только `can_claim_ref_bonus`/`mark_ref_bonus_claimed`
по отдельности).
**Фикс:** добавлена функция `try_claim_ref_bonus` в `database.py`,
объединяющая обе операции.

### 9. Две сломанные кнопки в админ-панели
**Файл:** `handlers/admin.py`
- "Статус системы" импортировал `XUI_HOST` из `config.py` — такой переменной
  там нет (есть `XUI_URL`).
- "Системные настройки" импортировал `REF_BONUS_DAYS` из `constants.py` —
  такой константы там не было.
**Фикс:** исправлен импорт на `XUI_URL`; `REF_BONUS_DAYS` добавлена в
`constants.py` (значение 15 — то самое, что реально используется в
`subscription.py`/`handlers/keys.py` для этого бонуса).

## Серьёзные (искажали данные / частично ломали функциональность)

### 10. Платёж за подписку записывался в БД два раза
**Файлы:** `handlers/buy.py`, `webhook.py`
И для Stars, и для YooKassa платёж сначала записывался через `add_payment(...)`
сразу после получения денег, а затем — повторно внутри `subscription.deliver_key`
после успешной выдачи ключа. Это раздувало статистику доходов и сумму
`total_paid` в отчётах админ-панели.
**Фикс:** убраны предварительные вызовы `add_payment` из `buy.py` и
`webhook.py` — платёж теперь записывается один раз, только при фактической
успешной выдаче ключа (внутри `deliver_key`).

### 11. Удаление одного ключа сносило VPN-доступ по всем ключам пользователя
**Файл:** `handlers/start.py`
На панели 3x-ui у каждого Telegram-пользователя ровно один клиент
(идентифицируется по `email = tg_{user_id}`), но в БД бота у пользователя
может быть несколько строк в таблице `keys`. Удаление любого одного ключа
вызывало `delete_marzban_user(user_id)`, что удаляло единственного клиента
на панели — то есть рвало доступ для всех "активных" ключей этого
пользователя, хотя в БД формально удалялась только одна запись.
**Фикс:** клиент на панели удаляется только если удаляемый ключ —
последний оставшийся у пользователя.

### 12. Лимит устройств не применялся на панели
**Файл:** `marzban_client.py`
`limitIp` (ограничение по числу одновременных IP) был захардкожен в `0`
(без ограничения) независимо от тарифа — тариф "1 устройство" по факту
не ограничивал ничего.
**Фикс:** `create_marzban_user` теперь принимает параметр `limit_ip` и
передаёт его на панель; `subscription.deliver_key` передаёт реальное
значение из тарифа.

### 13. Прямое подключение к БД мимо общего пула
**Файл:** `webhook.py`
Запись pending-платежа YooKassa открывала отдельное соединение через
`aiosqlite.connect(DB_FILE)` напрямую, без PRAGMA-настроек общего пула
(`busy_timeout=30000`, WAL mode и т.д.) — риск `database is locked` под
нагрузкой.
**Фикс:** используется существующая функция `add_yookassa_pending` через
общий пул `database.py`.

## Мелкие (не критичны для работы, но искажали логику/мусорили код)

### 14. Опечатка в SQL-параметрах
**Файл:** `database.py`
`(referrer_id)` вместо `(referrer_id,)` — не tuple, упало бы с
`sqlite3.ProgrammingError` при вызове (функция оказалась мёртвым кодом из-за
п.16, поэтому на проде не проявлялось, но исправлено).

### 15. Падение в последний день месяца
**Файл:** `notifications.py`
`_wait_until_03_00` вычисляла "завтра" через `target.replace(day=target.day+1)`,
что вызывает `ValueError` 31-го числа месяца (день 32 не существует).
Поскольку вызов не был обёрнут в try/except, это тихо убивало фоновую
задачу бэкапов — бэкапы просто перестали бы происходить без единой записи
в логе.
**Фикс:** переход на `timedelta(days=1)` (корректно обрабатывает границы
месяца/года) + try/except вокруг цикла бэкапов с логированием.

### 16. Дублирующиеся функции в `database.py`
Были две версии `has_active_subscription` и `get_all_users_csv` —
Python использует последнее определение, первое было мёртвым кодом.
Удалены дубликаты, оставлены рабочие версии.

### 17. Дублирующая регистрация обработчика ошибок
**Файл:** `main.py`
`dp.error.register(error_handler)` вызывался два раза — при каждой ошибке
админу прилетало два одинаковых уведомления. Убран дубликат.

## Обновление от 26.06.2026 (после первого запуска)

### 18. 403 Forbidden при логине в 3x-ui, хотя те же креды работают в браузере
**Файл:** `marzban_client.py`
Бот получал `403 Forbidden` именно на запросе `/login`, при том что вход
тем же логином/паролем через браузер проходил нормально. Разница — заголовки
запроса: `httpx` по умолчанию отправляет `User-Agent: python-httpx/x.x`,
который многие reverse-proxy/WAF перед панелью (nginx с
`ngx_http_useragent_module`, Cloudflare, fail2ban по логам) блокируют как
небраузерного клиента, до того как запрос вообще попадёт в обработчик
логина самой 3x-ui — то есть дело не в пароле.
**Фикс:** все запросы к 3x-ui (логин и обычные API-вызовы) теперь
отправляются с браузероподобными заголовками (`User-Agent`, `Accept`,
`Origin`, `Referer`). Также добавлены понятные сообщения об ошибке вместо
голого "403 Forbidden", если проблема всё же не в заголовках (см. ниже).

**Если 403 всё равно остаётся после этого фикса** — значит блокировка не по
User-Agent, а одно из:
- IP-allowlist на панели или firewall сервера, не включающий IP бота;
- `fail2ban`-jail, забанивший IP после серии прежних неудачных попыток —
  проверьте `fail2ban-client status` на сервере с панелью;
- правило reverse-proxy, требующее точного `Host`-заголовка.

### YooKassa 401 Unauthorized (это НЕ баг кода, информация для проверки)
Код авторизации в `payments.py` и `payment_monitor.py` корректен (обычная
Basic Auth из `YOOKASSA_SHOP_ID:YOOKASSA_SECRET_KEY`, закодированная в
base64). 401 при таком коде означает проблему в самих учётных данных
в `.env`:
- `YOOKASSA_SHOP_ID` должен быть числом (ID магазина в личном кабинете);
- `YOOKASSA_SECRET_KEY` — без лишних пробелов/кавычек, актуальный
  (не отозванный) ключ, и важно не перепутать `test_`-ключ от тестового
  магазина с `live_`-ключом от боевого.

## Обновление №2 (после диагностики 403 через curl)

### 19. 403 Forbidden оставался даже с браузерными заголовками — переход на localhost для API-запросов
**Файлы:** `config.py`, `marzban_client.py`

Диагностика показала: тот же самый запрос (`curl -X POST .../login` с теми
же логином/паролем) получает 403 **даже без единой строчки Python-кода**,
при том что вход в панель через браузер на том же домене работает нормально.
Добавление браузерных заголовков (User-Agent/Origin/Referer, см. п.18) не
изменило результат — значит блокировка не по заголовкам запроса. Сама
панель (`x-ui` 3.4.1) слушает порт напрямую, без отдельного nginx/Caddy
перед ней (подтверждено через `ss -tlnp` на сервере) — значит блокировка
происходит на уровне внешней сетевой фильтрации хостинга или в обработке
запросов через публичный домен самой панелью, но не в формате HTTP-запроса
как такового.

Все найденные рабочие примеры автоматизации 3x-ui (community Postman-
коллекция, сторонние API-клиенты на PHP/Node.js, актуальные установочные
гайды) обращаются к панели через `127.0.0.1` с того же сервера, а не через
публичный домен — это стандартная практика для таких панелей, не обходной
приём для конкретно этого случая.

**Фикс:** добавлена `XUI_API_URL` (`config.py`) — отдельный адрес для
внутренних запросов бота к панели (логин, создание/изменение клиентов).
По умолчанию вычисляется автоматически из `XUI_URL` заменой хоста на
`127.0.0.1` (тот же порт и секретный путь сохраняются — менять `.env`
не обязательно, если бот и панель на одном сервере). Публичная
`subscription_url`, которую получает пользователь в Telegram, **продолжает
строиться через `XUI_URL`** (настоящий домен) — это не меняется, конечному
пользователю всё равно нужно подключаться через интернет, не через
localhost бота.

Если бот и панель работают на **разных** серверах — задайте `XUI_API_URL`
в `.env` явно (адрес, по которому бот реально может достучаться до панели
в своей сети); автоматический localhost-дефолт в этом случае не подойдёт.

## Что НЕ было изменено (сознательно)

- Реферальный бонус начисляется двумя независимыми механизмами
  (`add_referral_earning` в момент оплаты — деньги, и `process_payment_referral_bonus`
  — дни). Это два разных, специально разделённых начисления, не дублирование
  одного и того же — оставлено как есть.
- `vless_links` в ответе `create_marzban_user` остаётся пустым списком — проект
  использует доставку через `subscription_url` (для v2rayNG/Happ/Nekoray),
  а не прямую `vless://` ссылку. Чтобы строить прямую ссылку, нужны
  REALITY-параметры (public key, short id, sni, fingerprint), которые сейчас
  не читаются из `.env` ни в одном файле проекта — это отдельная фича, не баг.

## Перед запуском в продакшен

1. Заполните `.env` на основе `.env.example` (особенно `BOT_TOKEN`, `ADMIN_ID`,
   `XUI_URL`/`XUI_USERNAME`/`XUI_PASSWORD`, `XUI_INBOUND_IDS`, реквизиты YooKassa).
2. Убедитесь, что процесс, под которым запускается бот, имеет права на запись
   в директорию проекта (для создания `data/vpnbot.db`).
3. Для приёма вебхуков YooKassa нужен публичный HTTPS-адрес, проксирующий на
   порт из `WEBHOOK_PORT` (см. `config.py`) на путь `/webhook/yookassa`. Если
   такого адреса пока нет — бот всё равно будет работать через
   `payment_monitor.py` (опрос YooKassa каждые 30 секунд), просто с задержкой
   до ~30 секунд вместо мгновенной обработки.

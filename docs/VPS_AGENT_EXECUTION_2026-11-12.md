# Задание агенту на VPS — ByMeVPN PR #95

Исходники подготовлены в ветке audit-remediation-2026-11-12. Берите самый свежий SHA самой ветки, а не SHA, записанный в старом чате. До успешной проверки на staging НЕ вносите изменения в production.

## Что нельзя менять

По решению владельца исключены пункты аудита 1.2, 1.4, 3.1, 3.5, 4.4, 5.2, 6.1 и 6.2. Без отдельной задачи не менять цены, длительности тарифов и подарочных месяцев, условия рефералок, бонусы за рекламу или автопродление по умолчанию.

## 1. Инвентаризация (read-only)

- Зафиксировать фактические primary и secondary Compose-файлы, Docker-образы, их digest, содержимое mount-путей и реальные SHA исходников в контейнерах.
- Проверить наличие вне-GitHub Python overlays и другого исходного кода, который подменяет файлы репозитория. Нельзя молча перезаписать незадокументированные production-изменения.
- Определить реальные каталоги SQLite, API и nginx, Redis, панели 3x-ui, Xray и защищённого хранилища. Исторические IP и пути не считать актуальными.
- Проверить конфликтующие PR #85 и #94; не сливать их автоматически с #95.

## 2. Резервирование и миграции (изолированный стенд)

- Выполнить онлайн SQLite backup (включая WAL), шифровать копию до передачи за пределы VPS. Отдельно сохранить необходимые Compose/systemd/nginx конфиги и неразглашаемые секреты в доверенном хранилище.
- В отдельной копии БД проверить scripts/verify_sqlite_restore.py и scripts/audit_email_identity_ids.py. Отчёт должен содержать только агрегаты, а не email, токены или данные платежей.
- Создать проверенную точку отката с конкретным SHA, digest образа, схемой базы и возможностью восстановления; провести dry-run восстановления в другом каталоге/контейнере.
- Настроить BYMEVPN_BACKUP_PASSPHRASE: случайный секрет от 32 символов, хранящийся вне VPS. Не публиковать секреты ни в GitHub, ни в чате, ни в логах.
- В staging задать BYMEVPN_RELEASE_SHA, BYMEVPN_BUILD_TIMESTAMP, BYMEVPN_IMAGE_DIGEST с реальными значениями сборки. Проверить, что админка отражает реально запущенный образ.
- Выполнить scripts/release_gate.py на staging-копии БД с аргументами --db и --expected-sha. Он проверяет локальные предпосылки, НЕ реальный VPN-трафик.

## 3. Стейджинг-проверки API, авторизации и платежей

- Выполнить Python test suite с Python 3.11 на актуальном SHA, обе GitHub Actions проверки должны быть зелёными.
- Проверить GET /healthz и /readyz в реальном приложении, отказ без авторизации на /api/v1/servers.
- Пройти новые/старые email-логины, Google и Telegram, старые PBKDF2 и новые scrypt-хеши.
- Проверить refresh-токены rf2_ и обмен старых ref_ токенов. Одновременные одинаковые запросы должны выдать не более одной новой сессии; повторное использование старого JWT должно отказать. После удаления аккаунта ни один refresh не должен восстановить доступ.
- Проверить 3x-ui: существующие подписки не теряют UUID; при неопределённом expiry не добавляются фиктивные дни; при сбое получения конфигурации клиент видит отдельную ошибку, а купленный срок не удаляется.
- В YooKassa sandbox проверить новые/повторные платежи, idempotency, отложенный webhook, падение между созданием счета и выдачей, сверку monitor, продление конкретного ключа, отзыв будущих списаний без отзыва оплаченных дней. Отдельно протестировать CryptoBot/Telegram Stars в разрешённом тестовом окружении.
- Проверить read-only журнал проблемных платежей в админке, отсутствие двойных выдач и фиктивного суммирования RUB с XTR.
- Проверить шифрованный .bmbackup, офлайн-расшифровку, восстановление в staging; отсутствие passphrase должно блокировать отправку незашифрованной копии.
- До любых операций с реальными аккаунтами: убедиться, что тесты удаления аккаунта не затрагивают других клиентов и не удаляют активные ключи панели.

## 4. Настоящий VPN-клиент и мобильная сеть

Для каждой доступной платформы Android, Windows, Linux и iOS (если подписанный билд существует): вход в приложение, распознавание уже оплаченной подписки, получение настоящего конфига, успешное установление туннеля, передача трафика, DNS, IPv4/IPv6, повторное подключение после рестарта и смены сети. Проверить Wi-Fi и мобильную сеть там, где они доступны. Метка active или HTTP 200 не является доказательством передачи трафика.

## 5. Развёртывание и откат

- Только после полностью зелёного staging и явного разрешения владельца — canary production с тестовым аккаунтом, не с реальными платящими клиентами.
- Не создавать вторые конкурирующие polling/webhook workers и не терять очередь событий.
- Сравнить фактические SHA и digest после запуска, запустить health/readiness, авторизацию, тестовое продление и настоящее VPN-подключение.
- При откате сохранять платежи, уже полученные во время окна релиза. Не заменять новые данные старым SQLite-файлом вслепую.

## 6. Отчёт

Вернуть владельцу PASS/FAIL/BLOCKED для каждого сценария, проверенный SHA и digest, дату, а также чёткий статус DEPLOYED или NOT DEPLOYED. Отдельно указать реальные проверки трафика, число инцидентных платежей (без ID), результат восстановления бэкапа и блокирующие условия. Если нельзя протестировать реальные устройства, провайдера или миграцию — пометить BLOCKED, не объявлять всё завершённым.
